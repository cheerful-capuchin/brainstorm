# Decision: Test Setup for the Databento Historical Replay

Date: 2026-09-20
Status: accepted (demo scope)
Related:
- [Backtest Historical Replay walkthrough](../2026-09-20-hist-replay.md)
- [Bucket Structure for Databento Historical Market Data](2026-09-20-hist-replay-bucket-structure.md)
- [Historical Replay Ingress for Databento Files](2026-09-20-hist-replay-ingress.md)

## Context

Agents will implement the Databento replay (`DbnFileStream`, route driven planning, the shared
path crate). They need a way to check their own work without a person in the loop, and the checks
have to give the same answer on every machine.

Facts this decision relies on:

- A full day of ES MBP-1 is a few hundred MB compressed. That is too large for plain git and too
  slow for `just check`.
- `structure-strat-template-core` is a library that every strategy pulls in as a git dependency
  (`structure-strat-template/Cargo.toml:18`). Anything added to its dependencies or its repository
  reaches every strategy build.
- `git-fetch-with-cli = true` is set in the workspace, in this crate, and in the Docker build.
- The crate already has a bin (`src/bin/dev_main.rs`) and a `run-backtest-local` recipe that runs
  it with `--regime backtest --warehouse-dir … --start-ts … --stop-ts … --outfile …`.
- `structure-strat-template-core/mnt/historical-data/databento/` exists and is empty. The repo has
  no `.gitattributes`.
- The walkthrough found that replay subjects (`md.instruments.…`) never match `FeedRoutes` keys
  today, and nobody has confirmed a working backtest by running one. There is no green end to end
  baseline to protect.
- A backtest that replays nothing still exits cleanly.

## Decision

Two levels of test, each with its own data.

| Level | Data | Runs in | Needs |
|---|---|---|---|
| Unit and integration | small DBN slices in plain git | `just check` | nothing external |
| End to end | full days in git LFS | `just e2e-backtest` | `git lfs pull` once |

Neither level needs the Databento API key. Only the download program does, and only a person runs
it.

### Small slices for `just check`

```
structure-strat-template-core/test_data/databento/GLBX.MDP3/mbp-1/{InstrumentId}/{YYYY-MM-DD}.dbn.zst
```

- Two instruments, two consecutive dates each, in the decided path layout: `ESU6`
  (`inst_CWQ5SAHD9NMGC`) and `CLV6` crude oil (`inst_4NKTGSW9TJ0AX`), 2026-09-10 and 2026-09-11.
- Each file is cut from a real download by `src/bin/slice_hist_data.rs` (`just slice-hist-data`):
  2,000 records, about 40 KB. The program keeps the input's DBN header and file name, refuses a
  slice without an `action == T` record, reads the slice back before giving it its final name, and
  removes a rejected slice.
- The 09-10 slice is the last 2,000 records of the day and the 09-11 slice is the first 2,000.
  The two are contiguous across UTC midnight, so a test window can cross the file boundary with
  no gap in the data. This replaces the earlier idea of cutting from a busy stretch. Every slice
  holds trades (87 to 372).
- The files are real Databento output, so they carry a true historical header: `ts_out` is off and
  records are 80 bytes.
- A slice does not cover its whole UTC day. Tests pick windows inside the slice.
- These files stay in plain git. They are never matched by the LFS pattern.

Cases that real data does not give on demand are written inside the test with the `dbn` encoder
and a temp dir: an empty day (header only), a record exactly at `max_ts`, and a missing file.

### Full days in git LFS

```
structure-strat-template-core/mnt/historical-data/databento/GLBX.MDP3/mbp-1/{InstrumentId}/{YYYY-MM-DD}.dbn.zst
```

- `warehouse_dir = mnt/historical-data`. The decided layout starts at `databento/` below it, so
  the local directory mirrors the bucket.
- Dates: 2026-09-10 and 2026-09-11, contract `ESU6` (`inst_CWQ5SAHD9NMGC`, `security_id`
  42140870). Daily volume from Databento shows these as the busiest pair of consecutive days for
  either ES contract in September 2026: 1.52M and 1.46M contracts, the last two days before volume
  moved to `ESZ6` on 2026-09-14. The files hold 8.83M and 8.78M records (452k and 442k trades) and
  are 162 MB and 163 MB.
- `ESU6` expired on 2026-09-18. An expired contract suits a pinned test, because its data and its
  market info no longer change. A second instrument is added if the demo strategy trades more
  than one.
- A second data set, `CLV6` crude oil on NYMEX (`inst_4NKTGSW9TJ0AX`, `security_id` 716552), is
  downloaded for the same two dates: 62 MB and 64 MB. Among the commodity futures in
  `market-info/assets/markets.csv` it had the second highest volume on those days (300k and 272k
  contracts) after micro gold `MGCZ6`, and it is the standard sized front month contract.
- `.gitattributes` gets one entry: `mnt/historical-data/**/*.dbn.zst filter=lfs diff=lfs
  merge=lfs -text`.

### Download program

A new bin, `src/bin/download_hist_data.rs`, fills `mnt/historical-data`. A person runs it to
produce or refresh the LFS data. No test runs it.

- **Request:** `timeseries().get_range_to_file`, dataset `GLBX.MDP3`, `Schema::Mbp1`,
  `SType::InstrumentId` with the Globex `security_id`, `start = date`, `end = date + 1 day`, DBN
  with zstd. This is the request the Cloud Run job in the bucket structure decision makes, so the
  local files are what production will write.
- **The client re-encodes.** The `databento` crate does not expose the raw response bytes. It
  decodes the stream and encodes it again into the file. The client is built with
  `VersionUpgradePolicy::AsIs`, so the records and the metadata are the ones Databento sent; only
  the zstd framing differs. This is a small departure from "exactly as Databento returns it" in
  the bucket structure decision.
- **Availability check:** the program reads the dataset's available range and refuses a day that
  is not fully available, as the Cloud Run job does.
- **Arguments:** domain instrument id, security id, a date or date range, output root (default
  `mnt/historical-data`), `--max-cost-usd` (default 5), `--force`.
- **Paths** come from the shared path crate of the bucket structure decision. That crate is built
  first.
- **Existing files are skipped** unless `--force` is given.
- **Writes go to a temp name and are renamed when complete.** A local disk has no all or nothing
  upload, and a truncated file at the final path would read as a short day.
- **Cost guard:** the program calls `metadata().get_cost`, prints the result, and stops if it is
  above `--max-cost-usd`.
- **Dependency gating:** `databento` is an optional dependency behind a `hist-data-download`
  feature, and the bin sets `required-features`. Strategy builds do not compile it.

### End to end recipe

`just e2e-backtest`, separate from `just check`:

1. Check that every expected data file starts with the zstd magic bytes. If one does not, fail
   with a message that says to run `git lfs pull`.
2. Run `dev_main` in the backtest regime against `mnt/historical-data` with a fixed config, start,
   stop, and an outfile in a temp dir. The demo strategy has no warmup, so the main window itself
   crosses UTC midnight between the two downloaded days. That puts the file boundary inside the
   run.
3. Assert: exit code 0, replayed tick count above zero on each of the two days, and the JSONL
   outfile holds more than the t=0 baseline record.

The strategy config used here declares only book and trade feeds for the downloaded instruments.

If the backtest does not already report a tick count that the recipe can read, adding one is part
of this work. The outfile alone cannot tell "replayed nothing" apart from "replayed but never
traded".

### Before the first LFS push

1. Push one LFS file on a branch, point a strategy at that rev, and check the size of
   `~/.cargo/git/checkouts/structure-strat-template-core-*`. The expectation is that cargo checks
   out pointer files only. This has not been verified.
2. If the data does come down, set `GIT_LFS_SKIP_SMUDGE=1` in the strategy build environments,
   including the Docker build.
3. Check the org's LFS storage and bandwidth quota against a few hundred MB per full clone. CI
   jobs that do not run the end to end recipe skip the LFS download.

### What agents are told

- `just check` must be green before work starts. If it is not, that is fixed or recorded first, so
  that existing breakage is not confused with new breakage.
- The end to end recipe starts red. It is the acceptance target, not a regression test. The first
  failures are expected in route planning and subject matching, and those are fixed, not worked
  around.

## Rationale

**Data in the repo instead of a download step in the test.** Every machine and every agent run
sees the same bytes, the test needs no network and no key, and Databento is paid once. A download
step inside the test would make each fresh checkout spend money and would hand the key to agents.

**Two data sets instead of one.** `just check` has to work in a checkout where nobody ran
`git lfs pull`. There an LFS file is about 130 bytes of pointer text, and a test reading it fails
with a DBN decode error that says nothing about the cause. Small slices in plain git keep the fast
tests independent of LFS.

**Real slices instead of only synthetic records.** The provider has to handle what Databento
writes: the historical metadata header and 80 byte records without `ts_out`. A fixture built with
our own encoder would only prove that we can read what we wrote.

**The same request as production.** The download program and the Cloud Run job differ in where
they write, not in what they ask for. A replay that works on the local files works on the bucket.

**A feature gate for the download bin.** The library is compiled into every strategy. Without the
gate, the `databento` client and its HTTP stack would be too.

**An explicit tick count in the pass rule.** The failure mode that matters most for the demo is a
backtest that finishes cleanly after replaying nothing. Exit code and outfile presence do not
catch it.

## Consequences

- `structure-strat-template-core` gains `.gitattributes`, a `hist-data-download` feature, a second
  bin, and an `e2e-backtest` recipe.
- Contributors who run the end to end recipe need `git lfs` installed and one `git lfs pull`.
- The LFS data is pinned to two dates and one expired contract. If `ESU6.ron` is removed from
  market info or marked inactive, and the strategy config loader rejects such instruments, the end
  to end recipe breaks for a reason unrelated to replay. Whether the loader does that has not
  been checked.
- Refreshing data costs a Databento request and an LFS upload. Both are manual.
- `prototypes/replay/src/bin/download_sample.rs` is left as it is. It downloads MBO through the
  batch API and is not part of this setup.

## Findings from the first download

- Databento quoted $0.00 for both days under the current plan.
- In both files `ts_recv` never decreases, and `sequence` never decreases either, including
  inside runs of equal `ts_recv`. About 6% of records share `ts_recv` with their predecessor.
  File order is therefore a valid replay order for one instrument. This answers, for these two
  days, the open item about `sequence` in the bucket structure decision.
- The metadata header is as assumed: DBN version 3, `ts_out` off, `start` and `end` on the exact
  UTC day bounds.

## Out of scope

- The Cloud Run download job. The bucket structure decision covers it.
- Running the end to end recipe in CI. It is a local recipe for now.
- Live warmup. It is the open question in the bucket structure decision.
- Performance targets for replay. The end to end run shows the time; nothing is asserted on it.
