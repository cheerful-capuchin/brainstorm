## Questions

### 1. How do we define the input types and the domain traits those inputs should be transformed to?
The way I think about the services, is that you have the input contract and the validated message your domain code is actually working with.
For instance:
```
request ListMarketsRequest {
    correlation_id: u64,
    limit: u32,
    cursor: string
}
```
can be the input contract, while my service actually handles
```rust
pub struct CorrelationId(u64);
#[derive(Copy)]
pub struct Limit(u32);
impl Limit {
    pub const UNSPECIFIED: Limit = Limit(0);
    fn or_default(&self, default: u32) -> Limit {
        if self == Self::UNSPECIFIED {
            return Limit(default);
        }
        self
    }
}

pub struct Cursor(Arc<str>);
impl Cursor {
    // ...
}

pub trait ListMarketsRequest {
    fn correlation_id(&self) -> CorrelationId;
    fn limit(&self) -> Limit;
    fn cursor(&self) -> Cursor;
}
```

and those newtypes may include more validation rules. e.g.
```
pub struct String128(Arc<str>);
impl String128 {
    pub const SIZE: u32 = 128;

    pub fn try_new<S: AsStr>(maybeStr: S) -> Result<Self, Error> {
        if maybeStr.trim().len() > Self::SIZE {
            return Err(...)
        }
        return String128(maybeStr)
    }
}
```

How do you handle this, do you specify all those domain types on the contract, which sounds like something quite useful,
or do you keep the contract with wide types and then create separate traits?

I'm torn between these options since the user may not have the same validation capabilities you have, but if you use the loose types, then you're lying about the contract.
