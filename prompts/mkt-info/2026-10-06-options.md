brainstorm/sessions/SESS-00PXT2F-cme-options-market-info.md
The current approach for storing the mkt info data is a set of text files in market-info/assets.
When I analyzed the secdef from CME market-info/crates/cme-market-info-gen/assets/secdef.dat.gz, there are 947,092 definitions available for the next trading session.
Out of them, 790,315 are options.

We want to integrate the options markets, and I don't think having text files is a reasonable solution anymore.
Even if, we put all the options strike prices into a single file, it's still a lot of files.
We already had an idea of market-info/crates/market-info-server, which will manage everything related to market info.

With time, I imagine, there will be even more markets as more and more of them created every day.
How do we store all of them and how do we serve them to the exising infrastructure?

Additionally, we want to backfill the historical information, which implies all the markets starting from around 2010 (databento cut off).
I imagine that's a lot of markets. We use hashing to create an instrument id. Instrument id is a u64.
We'll start having collision problems after 2 billion entries with a 50% chance.

What do we do?


Well, I imagine we have 2 responsibilities here:
- historical log of the changes over time
- what's the state at the current moment in time

If all the historical events are folded, we know the state at any moment in time.

We'll have a separate service that handles the storage of the historical mkt data.
The historical mkt data is immensely useful for backtest and replay.
However, when I just want to know the state at NOW, I don't want to go and replay all the events.

Additionally, there is information that we add by ourselves to each market definition.
A presentation information like display_name, for instance.

When the user is requesting: give me all the future markets for ES product since 2010, I don't want to send them a stream of events
they need to accumulate, I want to send the snapshots.

So, the question is: where and how do we store the data.
I could have the historical changes and data be stored in flat files, like I already do in knowledge-base/docs/references/databento-market-data.md,
but then I would need some snapshots, so I can replay the state faster.

I could have everything be in RAM, but that's going to end very quickly and badly.

I could store data in historical flat files and in postgres/duck db database.

I could use duck db with ephemeral disk only for the duration of the service and just take more time to boot up and load the database.
Then have a tiered storage, where the "hot" markets are in ram and the less popular ones are in ssd.
Every mutation from the structure staff fires an event that the historical data must store, so I can restore everything once the process
reboots.
Every list/query is going through the market data server, so no one has direct access to that duck db.
Maybe I don't even need a duck db and I just have some fast indexed storage/LSM/rocksdb/etc.
