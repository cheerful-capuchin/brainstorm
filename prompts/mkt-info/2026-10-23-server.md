I want to talk about the distinction of the layers when designing the contracts of the services.
For instance, we have the market info server market-info/crates/market-info-server.
The goal of the server is to serve the market info from market-inf/assets/market-info.rkyv

All the services within our VPC and outside should be able to query the market info.

However, the more I study the different services, the lines become blurred.
You have the transport encoding, then you add the meaning to the bytes you get. These 8 bytes are interpreted as a number,
those 2 bytes are 2 boolean flags, those 24 are text of 20 chars and 4 bytes are the length of the text, etc.
You add additional constraints within your domain, e.g. the number must be greater/less than X, text must have this length or this structure, etc.

I think GCP APIs are the best example here.
There, they can declare in the protobuf definition, e.g. https://github.com/googleapis/googleapis/blob/master/google/cloud/secretmanager/v1/service.proto

```
// Request message for
// [SecretManagerService.ListSecrets][google.cloud.secretmanager.v1.SecretManagerService.ListSecrets].
message ListSecretsRequest {
  // Required. The resource name of the project associated with the

  // or `projects/*/locations/*`
  string parent = 1 [
    (google.api.field_behavior) = REQUIRED,
    (google.api.resource_reference) = {
      child_type: "secretmanager.googleapis.com/Secret"
    }
  ];

  // Optional. The maximum number of results to be returned in a single page. If
  // set to 0, the server decides the number of results to return. If the
  // number is greater than 25000, it is capped at 25000.

  // Optional. Pagination token, returned earlier via
  // [ListSecretsResponse.next_page_token][google.cloud.secretmanager.v1.ListSecretsResponse.next_page_token].

  // Optional. Filter string, adhering to the rules in
  // [List-operation

  // listed.
  string filter = 4 [(google.api.field_behavior) = OPTIONAL];
}
```

Here, the transport encoding is mixed together with the service RPC, with some constraints about the semantic meaning of the data,
and some additional items like `[
(google.api.field_behavior) = REQUIRED,
(google.api.resource_reference) = {
child_type: "secretmanager.googleapis.com/Secret"
}
]`, which I don't know much about, whether they influence the behaviour in any way or does this just act like a comment.

Then, you have the part where you want to remove the menial task of building the clients and, instead, generate the request builders/encoders
as well as response decoders and parsers.

On the server side, you would like to use the domain types you have, like `Venue`, `InstrumentId`, `InstrumentType`, etc.

The transport messages don't describe the contract of the service well.
Having comments and plain text is a way to do that, but not a very reliable one.

Let's sort this out and figure out the different layers between the encoding, the semantic meanings behind the bytes, the constraints,
the domain layer and the specification of the contract.
